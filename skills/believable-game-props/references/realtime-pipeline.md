# Blender, export, and gameplay verification

## Isolate the problem

- Use Workbench or a neutral material override with a fixed broad light, camera and exposure. Turn off color textures, baked occlusion, decals and detail normals. Compare an uncluttered outline and an in-context capture. Disable cavity effects when judging real contact. Compare a second light angle to tell an edge or normal gradient from the light. Compare object and section views when a gap is in question.
- Give a machined part and a padded part different edge constructions. A physical bevel supplies actual profile and specular catch. Custom/weighted normals can help rigid planar faces stay visually flat but do not repair bad topology or create volume. Compare with modifiers toggled in a copy. Check evaluated triangulation, smooth/sharp splits, final corner normals and tangent consistency in what the exporter actually writes. Use Blender documentation for the installed release.
- Use a scaled UV checker. Start from world dimensions and neighboring assets, then verify scale with a swatch or known size. Average island scale can help with consistent density, not intentional grain direction or absolute scale. Check stretching, mirrored directional patterns, padding across mip levels, grain at seams, and unique readable labels. Match the bake UVs, mesh splits, triangulation and target tangent convention.
- In shared light, judge highlight width, strength and motion separately from base color. Use the following material observations as heuristics. Woven fabric usually softens and breaks up the highlight. Leather varies widely by finish and needs plausible pores. Plastics range from matte to glossy. Glass adds an angular reflection relative to adjacent housing. Wood and polished stone retain coherent grain and veining. Bare metal and paint on metal should not react identically. Use surface samples and target-shader inputs, not presets based only on those labels. A nearby display can be useful as a runtime control, provided its finish, angle and reflection inputs are comparable.

## Spend detail at the player camera

- Test the normal path, nearest allowed view, and a grazing view if it can occur. Record on-screen size at target resolution where useful. Put visible silhouette, physical gaps, major construction breaks, and motion/parallax in geometry. Use bake relief for shallow quilting, fine seam shadow and gentle stamped detail if it survives mip filtering. Use texture or masks for legends and face variation. Faint detail that vanishes, flickers or moirés is a candidate to simplify or omit.
- Preserve silhouette and parts that explain the construction as LOD decreases. Remove hidden detail first. Check LOD transitions in motion, not just stills. Compare exported triangle/vertex and material-section counts, texture memory or streaming, shader overdraw and actual draw/render cost against a known-good prop and this project's constraints. Counts are context, not a pass or fail by themselves. Combine compatible opaque sections or use shared materials/atlases where profiling supports it and UV/readability still hold. Keep different shaders or render states separate when needed.
- Blender material/Workbench preview is a diagnostic. Blender Principled layers and the preview HDRI are not a target-engine shading contract. Normal-map RGB is data. Verify target tangent orientation, texture compression, color-space assumptions, alpha semantics, and mip behavior with a known-good asset and an asymmetric test swatch. Do not flip the green channel or repack channels by assumption.

## Conditional GTA V / Sollumz / FiveM route

Use only after confirming this pipeline. Record Blender, Sollumz, dependency versions, platform, exact GTA/FiveM build and Legacy/Gen8 or Enhanced/Gen9 target. Inspect a representative source, resource manifest, export preset, and a known-good streamed prop. Do not infer installed versions or settings from a screenshot or documentation.

1. Check the installed export UI, dependencies, docs/release notes, and a representative asset before choosing native binary or CodeWalker XML/compile. The older Sollumz feature docs and Cfx tutorial cover an XML-era workflow. Sollumz 2.8.0 release notes document native import/export for supported resource types via optional PyMateria, Windows-only at that release. Later releases may differ. Verify what the project can actually export and load.
2. For a suitable opaque surface needing diffuse, tangent normals and specular texture, consider the documented `normal_spec` candidate. The Sollumz tutorial maps `DiffuseSampler` to color, `BumpSampler` to normal, and `SpecSampler` to specular. Confirm the exact preset and serialized identifier/extension, sampler names and UV sets in the installed shader definitions and exported asset. Check non-color normal preview setup in Blender and independently check runtime direction and any channel or alpha assumptions using a known-good sample. Do not substitute metallic or roughness directly for a specular map. For simple opaque surfaces without those inputs, or for transparent, tinted, emissive or special display materials, select a proven project shader supporting the actual behavior. Do not assign this preset to every prop.
3. Confirm drawable hierarchy, applied or evaluated transforms/modifiers, pivot, bounds, geometry/material sections and assignments at each used LOD. Inspect exported shader parameters and texture names/dictionaries, embedded vs external delivery, mips, texture paths and the resource's manifest or archetype registration if applicable. For a typical static drawable, check the YDR and related YTYP or dictionaries where the project uses them. Verify collision only where needed. Parse/reimport or inspect the compiled output with a compatible tool, then load that exact artifact in the target.
4. Pilot one foreground prop on a scratch/test resource only when authorized. Preserve art direction and placement. Match before/after camera, room lighting, exposure, distance and surface state. Walk the real player path. Check texture resolution and highlight behavior at a grazing view, LOD popping, and collision and failure logs as applicable. If export looks right but runtime differs, use a known-good material on the same geometry and the candidate material on a known-good comparable surface in separate controlled tests, where compatible. Vary one factor at a time. If the engine is unavailable, write “not verified in-game” and leave a capture, build and view test with exact steps.
